## 1. CONTEXTO DEL SISTEMA

### Descripción General
Sistema web de apoyo diagnóstico para clasificación de mamografías (benigno vs maligno). Combina 3 capas: frontend React, backend FastAPI y dashboard de entrenamiento Streamlit.

### Arquitectura en 3 Capas

```
USUARIO (Navegador)
    │
    ▼
┌─────────────────────────────────────────────┐
│ FRONTEND (React 18 + Vite 5 + Tailwind 3)   │
│ localhost:5173 (dev) / localhost:3000 (Docker)│
│ Componentes: Login, Header, Hero, UploadPanel│
│ ClinicalForm, ResultPanel, ConfidenceGauge,  │
│ HistoryList, Dashboard, HelpChatbot, Footer, │
│ Spinner, Tooltip                             │
│ Hooks: useDarkMode, useHistory               │
│ API: api.js (fetch wrapper)                  │
└──────────────────────┬──────────────────────┘
                       │ POST /predict, GET /health
                       │ GET/DELETE /history, POST /auth/login
                       │ GET /auth/me, GET /
                       ▼
┌─────────────────────────────────────────────┐
│ BACKEND (FastAPI + Uvicorn)                  │
│ localhost:8000                               │
│ Endpoints: /predict, /health, /history,      │
│   /auth/login, /auth/me, /                   │
│ Seguridad: JWT, rate limiting (slowapi),     │
│   CORS, validación uploads (security.py)     │
│ Modelos: 5 modelos con consenso              │
│   RF, XGBoost, CNN, CNN+RF, CNN+XGBoost     │

└──────┬───────────────────────────┬──────────┘
       │                           │

│ .keras, .pkl  │        │ 7 vistas, 10 módulos │
└──────────────┘        └──────────────────────┘
```

### Stack Tecnológico

| Capa | Tecnologías |
|------|-------------|
| Backend | Python 3.10, FastAPI, Uvicorn, Pydantic, PyJWT, slowapi, TensorFlow/Keras, XGBoost, joblib, OpenCV, gdown |
| Frontend | React 18, Vite 5, Tailwind CSS 3, JavaScript ES6+ |
| Training | Python 3.10/3.11, Streamlit, Pandas, Plotly, scikit-learn, XGBoost, ReportLab, python-docx, openpyxl |
| Infra | Docker, docker-compose, Nginx, GitHub Actions, Render (backend), Vercel (frontend), Google Drive (modelos) |

### Los 5 Modelos del Sistema

| # | Modelo | Tipo | Datos | Dónde se entrena |
|---|--------|------|-------|-----------------|
| 1 | **RF** | Random Forest | 30 características Wisconsin (tabulares) | Streamlit Dashboard o Colab |
| 2 | **XGBoost** | XGBoost | 30 características Wisconsin (tabulares) | Streamlit Dashboard o Colab |
| 3 | **CNN** | EfficientNet (Transfer Learning) | Mamografías 224×224 RGB | Google Colab (GPU) |
| 4 | **CNN+RF** | Híbrido: CNN extractor + RF clasificador | Imagen + features extraídas por CNN | Google Colab (GPU) |
| 5 | **CNN+XGBoost** | Híbrido: CNN extractor + XGBoost clasificador | Imagen + features extraídas por CNN | Google Colab (GPU) |

**Cómo se usa en la API:**
- `POST /predict` acepta: imagen (obligatorio) + 4 datos clínicos (assessment, subtlety, age, density) + 30 campos Wisconsin (opcional, con defaults).
- La API ejecuta los 5 modelos disponibles.
- Calcula consenso: `full_agreement` (todos coinciden), `majority` (mayoría), `disagreement` (sin acuerdo).
- Si faltan datos clínicos, ciertos modelos muestran "N/D" (no disponibles).
- RF se entrena localmente en Streamlit; CNN, CNN+RF y CNN+XGBoost se entrenan en Colab.

### Datasets Utilizados
- **CBIS-DDSM**: Mamografías (calcificaciones + masas) con metadatos DICOM. ~2.500 casos.
- **Wisconsin Breast Cancer Diagnostic**: 569 casos, 30 características morfológicas del núcleo celular.

**4.4.1 Flujo de Autenticación**

**4.4.2 Flujo de Predicción Completo**
Actor Usuario → UploadPanel (drag & drop) → App.jsx (validateClinical) → api.js (predictImage con FormData: file + clinical + wisconsin) → POST /predict → Backend security.py (validate_upload_image) → model_handler.predict_all(raw_bytes, clinical_data, wisconsin_data) → Ejecuta 5 modelos (CNN, Ensemble, XGBoost, CNN+RF, CNN+XGBoost) → compute_consensus → guarda en history deque → PredictionResponse JSON → Frontend ResultPanel + ConfidenceGauge + HistoryList

**4.4.4 Flujo de Dashboard**
Usuario → Header "Dashboard" → Frontend Dashboard → fetchHistory + checkHealth → GET /history + GET /health → Renderiza stats cards + tabla historial

**4.4.5 Flujo de HelpChatbot**
Usuario abre chatbot → escribe o usa voz (SpeechRecognition) → findAnswer() busca keywords en FAQ[] → responde con texto + TTS (SpeechSynthesis)

**4.4.6 Flujo de Entrenamiento (Streamlit)**
Usuario autenticado → selecciona página → exec(open(view)) → cada view usa módulos (eda, models, cv, tuning, stats, reports) → genera figuras Plotly → guarda modelos .pkl → exporta PDF/Word/Excel

#### 3.5 Diagramas de Estado (stateDiagram-v2)

**3.5.1 Estados de la Aplicación (App.jsx)**
- `login` → usuario no autenticado, muestra Login + HelpChatbot
- `home` → autenticado, muestra UI principal (Upload, ClinicalForm, ResultPanel, HistoryList)
- `dashboard` → autenticado, muestra Dashboard + HelpChatbot
- Sub-estados de home: idle → loading (sube imagen) → success (resultado) / error (fallo) → idle / loading

**3.5.2 Estados del Modelo (model_handler.py)**
- `not_loaded` → startup del lifespan
- `loading_model` → load() descarga de Google Drive o carga local
- `loaded` → listo para predict
- `predicting` → predict_all ejecutando modelos
- `error` → falló la carga
- Transiciones: not_loaded → loading_model → loaded/predicting/error → shutdown

**3.5.3 Estados del Historial (deque en memoria)**
- `empty` → sin predicciones
- `populated` → con 1-49 items
- `full` → 50 items (FIFO: nuevo reemplaza al más antiguo)
- Transiciones: empty → POST /predict → populated → POST /predict → full; cualquier estado → DELETE /history → empty

**3.5.4 Estados de Autenticación**
- `unauthenticated` → sin token
- `authenticated` → token válido en localStorage
- `token_expired` → JWT expirado (redirige a login)
- Transiciones: unauthenticated → login exitoso → authenticated; authenticated → logout/token expirado → unauthenticated

**3.5.5 Estados del Upload/Análisis**
- `idle` → esperando imagen
- `validating` → cliente valida tipo/tamaño
- `uploading` → enviando a backend
- `processing` → backend ejecutando modelos
- `success` → resultado recibido
- `error` → fallo (red/API/validación)
- Transiciones con retry y clear
